# Context Governor 验证计划

本文固定 Governor 的正确性验证策略。目标是先确认整个机制在不同任务、不同 Context 窗口下正确工作，再单独讨论成本、速度和工具调用次数。

## 1. 测试集（已冻结）

本轮首先验证 Governor 在 LOCA-bench 的不同任务类型和不同上下文压力下，是否保持任务正确性。测试集不按既有运行结果挑选；任务族、环境实例和规模均由下列固定规则决定。

### 1.1 选取规则

- **任务覆盖**：纳入 LOCA `final_*_set_config.json` 中全部 15 个任务族，不只测试 Canvas 类任务。
- **环境实例**：每个任务族固定选取第 1、第 3、第 5 个实例，即 seed `42`、`456`、`2024`；它们对应每族五个配置中的相对位置 `0`、`2`、`4`。
- **环境规模**：每个实例分别运行 LOCA 的 `16K`、`32K`、`64K` 配置。
- **不可事后挑选**：同一任务族剩余的 seed `123`、`789` 不参与本轮；不得根据任务难度、已有结果或模型表现替换已选实例。

`16K`、`32K`、`64K` 指 LOCA 生成的环境数据规模与由此带来的上下文压力，不是模型 API 的上下文窗口上限。模型窗口、模型版本、DSH 版本、Adapter 版本和 Governor 代码版本将在每轮运行清单中另行固定。

## 2. 固定原则

- 同一轮验证中固定 Governor 代码、DSH 版本、模型、Adapter 版本、LOCA 配置和 Fixture 哈希。
- 正确性阶段允许记录公平的 DSH 原生基线对照，但不以节省 token、耗时或工具调用次数替代正确性；性能数据只作为观察项。
- 每次运行必须保留 `evaluation.json`、`run.json`、Governor Session 工作区和 Audit，保证结果可复核。
- 任何一个任务输出错误、生命周期未完成或 Governor 持久化不一致，整轮正确性验证均不通过。

## 3. 验证目标

Governor 的正确性不只由最终任务答案决定。一次运行只有同时满足以下五类目标，才能说明其上下文管理过程可靠。

### 3.1 任务成功率（硬门槛）

任务输出必须通过 LOCA 自带 evaluator：

```text
任务成功率 = evaluator 通过的有效运行数 / 有效运行总数
```

通过条件是 `evaluation.status = success`、`accuracy = 1`，且 Governor 的 `lifecycle.status = completed`。`status = success` 本身只表示验收成功执行，不代表任务通过。

同时报告成功数／全部计划运行数、已完成验收数／全部计划运行数，以及失败、超时未完成、基础设施错误的数量。只对已完成验收计算的成功率必须注明分母，不能排除超时后宣称整体通过。模型 API 故障、Adapter 崩溃等基础设施问题单列，不冒充业务失败，也不悄悄删除。

### 3.2 Step 与 SubStep 划分准确性

计划必须完整表达任务要求，并把当前工作拆为合理、可推进的 SubStep。它不是只检查“是否创建了计划”，而是检查计划是否漏项、重复、越界或伪完成。

例如，任务要求检查全部课程、应用公告免交规则、筛选作业和测验、生成两个 CSV，则计划必须覆盖这四类结果；不能把“检查全部课程”缩小为“检查部分相关课程”，也不能在一个 SubStep 中混合数百项采集、规则解释、CSV 写入和最终验收。

记录以下指标：

```text
Step 覆盖率
= 至少被一个 Step 覆盖的任务完成标准 / 全部任务完成标准

SubStep 覆盖率
= 至少被一个 SubStep 覆盖的当前 Step 完成标准 / 当前 Step 全部完成标准

计划违规率
= 存在遗漏、重复、越界或伪完成的 Step/SubStep 数 / 全部 Step/SubStep 数
```

结构性覆盖和状态流转由脚本检查；任务含义是否被错误缩小、SubStep 粒度是否合理，则结合运行证据抽样核验。

### 3.3 Artifact 等中间产物的准确性

Artifact 是供后续工作复用的精确数据，不是模型对旧工作的自由摘要。每个 Artifact 必须同时满足：

```text
资源真实：文件存在、绝对路径正确、哈希匹配、内容可解析。
结论可追溯：key_facts 能由资源内容或关联的 History 证据支持。
复用正确：后续工作没有将摘要误当完整数据，也没有使用过期或错误的 Artifact。
```

例如，名为“30 个未提交作业完整明细”的 Artifact，既要指向真实存在的 JSON 文件，也要确实包含 30 条明细；后续生成的 CSV 必须与该明细一致。

文件、哈希、格式和引用关系由脚本检查；`key_facts` 是否忠实概括资源内容、是否被正确用于后续决策，结合资源和运行轨迹抽样核验。

### 3.4 工具调用有效性

不能只看工具是否返回而不报错。每轮区分三种指标：

```text
调用成功率 = 正常返回的工具调用数 / 全部工具调用数
Schema 成功率 = 参数满足工具契约的调用数 / 全部工具调用数
有效调用率 = 返回结果确实支持后续决策或产物的调用数 / 全部工具调用数
```

例如，查询作业工具成功返回，但 Agent 只查了 10 门课程就声称已覆盖全部 135 门课程；这次调用在技术上成功，却没有支撑“已覆盖全部课程”的业务结论。前两项由 trace 自动统计；有效调用率结合 Step、Artifact 与最终结果核验。

### 3.5 Context 连续性与持久化正确性（硬门槛）

跨 Epoch 与跨 Session 时，Governor 必须保证 State、SubState、Artifact、History 与 Audit 的边界正确：

```text
- State 与 SubState 的引用一致，且当前 SubStep 属于当前 Step；
- 已完成的 Step 不会回退为 pending，也不会被伪完成；
- 每次成功的 State/SubState 变更立即原子落盘，revision 与工具返回一致；
- 新 Epoch 从最新持久化快照加载，事务中断可恢复；
- Continuation 在新 Epoch 从准确位置恢复；
- Artifact 只引用已验证的不可变资源，且不跨 Session 串用；
- 新 Session 不读取旧 Session 的 State、Artifact、Audit 或 History；
- Governor 回查接口产生可审计记录。
```

这类不一致即使没有影响 LOCA 的最终答案，也视为 Governor 正确性失败。

### 3.6 Context 安全线与性能观察项

Context 安全线属于功能性观察项，而非成本指标：每轮记录每个 Epoch 的压力和切换点。只要存在明显越过安全线后仍继续普通执行的情况，就不得宣称切换策略已经验证完成。

输入、输出、缓存和推理 token，耗时，工具调用总数，Epoch 数、切换次数、Continuation 次数和 Artifact 数均须记录，但本轮不作为通过条件；它们留作后续性能优化与 baseline 对照的共同基线。

## 4. 验证层次与顺序

### A. 代码级验证

修改 Governor 后，先按 [README 的测试说明](../README.md#开发与验证)运行全部单元与集成测试；要求零失败、零跳过。覆盖初始化、规划、状态推进、即时持久化、过时 revision 拒绝、事务中断恢复、标准修订、History 引用与 Artifact 同次提交。

修改实验接入时，运行 Adapter 自身的针对性测试；涉及容器路径、附件发送或隔离时补做无模型调用的 Docker 集成验证。两类测试结果分别记录，不能用 Adapter 测试代替 Governor 正确性测试。

### B. 真实任务与配对实验

当前 Adapter 已接入固定测试集所需的业务 Mock 与执行工具。具体能力、环境要求和命令以 `loca-dsh-adapter` 的 README 为准，不再保留旧的“先扩展工具才能运行”任务清单。

按范围逐步验证：

1. 先在受影响条件上做定向回归；实验接入修复对 Governor、Baseline 同等生效。
2. 再选取运行前声明的配对子集，覆盖不同任务族与数据规模。
3. 最后运行第 1 节完整冻结集合；不根据早期得分替换实例或缩小集合。

例如，seed 42 的 15 个任务族 × 32K/64K × 两种模式，共 60 次，是完整集合的一个回归子集，不改变原来的 135 条件定义。模型窗口是独立实验参数，不应与 LOCA 数据规模混淆。

Governor 与 Baseline 使用相同 Fixture 内容哈希、逻辑参考时间、模型与窗口、DSH 版本、工具契约和运行时限；只改变上下文管理方式。运行产物相互隔离，原始结果不覆盖。

### C. Context 连续性检查

数据规模大不代表一定发生 Context 切换。完成实验后，必须从实际 Audit/Trace 确认哪些运行发生切换，并抽查：

- 没有切换的短任务；
- 切换一次的任务；
- 多次切换及按需回查的长任务；
- 有 Artifact 的跨 Epoch 复用，以及未完成 SubStep 的 Continuation 恢复；
- 成功、业务失败、未完成及 Token/工具调用异常偏高的运行。

抽样覆盖不同任务族与 16K、32K、64K 规模。没有发生切换、没有产生 Artifact 或没有修订标准的样本，不能证明对应机制已被实际验证。抽样审阅使用紧凑证据包定位原始 Trace，不以摘要本身代替原始证据。

## 5. 每次 Benchmark 运行的固定记录项

每个运行目录必须记录并汇总：

```text
任务 ID、config-index、seed、Fixture 哈希、Context 窗口
evaluation.status、accuracy、feedback
lifecycle.status、State revision、Step/SubStep 数量
Epoch 数、切换次数、Continuation 次数、Artifact 数、检索读取数
每个 Epoch 的压力、切换原因与是否超过安全线
输入、输出、缓存、推理 token；耗时；工具调用数
```

官方结果、生命周期、状态与切换记录用于正确性复核；Token、耗时和工具调用数量用于效率观察。实验参数和运行目录只记录在实验产物中，不进入 Governor 的配置或策略。

## 6. 通过与下一阶段

进入性能优化前必须满足：

1. A 组自动化测试全部通过；
2. 第 1 节冻结的 135 次 Governor 运行全部 `accuracy = 1` 且 `lifecycle.status = completed`；
3. 不存在 State/SubState/Artifact/Audit 跨 Session 混用、伪完成或事务不一致；
4. 每个已纳入测试集的任务族所需 Adapter 能力均已实现；不得将 Adapter 不支持的任务当作通过或失败样本；
5. Context 安全线观察项没有未解释的越界执行。

若任何项失败，先定位并修复正确性问题；不以降低 token 或加快速度作为修复手段。

当上述条件全部满足后，冻结本计划所产生的运行数据，作为后续性能优化与 DSH 原生基线对照的共同基线。

## 7. 官方验收与检查边界

### 7.1 业务结果：使用 LOCA 官方 Verifier

```text
当前任务定义 / env_class
→ Adapter 解析该任务族的官方验证入口
→ 当前 Agent Workspace + 同一实例的 Ground Truth
→ 保留官方 accuracy、feedback 与执行状态
```

不同任务族各用自己的 Verifier；不同 seed、规模使用各自生成的 Ground Truth。同一配对的两个模式则共享同一个冻结实例。Adapter 不复制业务评分逻辑，不把某个任务族的判题器套到其他任务，也不更改任务或标准答案以规避失败。

验收进程必须定位到当前任务实例，包括官方入口使用的 `TASK_DIR`；容器文件引用只做必要的路径适配，不修改业务内容、忽略缺失文件或改变比较规则。无法解析或运行 Verifier 时记录 `verifier_error`，不能伪装成任务失败。

若发现 Benchmark 数据与标准答案不一致，保留官方结果，并单独记录异常证据及其影响；不要静默修改分数或从报告移除该条件。超时属于未完成，不能推断为业务结果错误。

### 7.2 Governor：全量结构检查与语义抽查

LOCA 不检查 Context 切换质量。对启用 Governor 的全部运行，Adapter 应只读检查：

- 是否意外触发原生压缩；
- State/SubState/Artifact 是否可解析、引用和状态是否一致；
- 已登记资源的存在性、路径、格式及哈希；
- Session 工作区是否隔离，是否存在结构上可发现的越界引用；
- Epoch Audit、切换基线和持久化记录是否可用于复核。

这些是结构检查，不能证明证据的业务语义。计划是否漏掉用户要求、SubStep 粒度、Artifact Key Facts、完成声明和回查选择，按第 4 节的分层规则由审阅者结合原始证据检查；不新增自动业务验证 Agent。

### 7.3 组件职责

| 组件 | 验证中的职责 |
| --- | --- |
| LOCA-bench | 任务、Mock、数据生成、Ground Truth 与业务验收 |
| Adapter | 环境接入、官方验收调用、结果采集、结构检查和报告 |
| DSH | Agent 运行时、模型请求、工具执行与会话记录 |
| Governor | 上下文管理、状态与交接一致性、通用 Guidance |
| Agent / 审阅者 | 执行业务及核对结论与证据的语义 |

## 8. 保留的待验证事项

以下事项从已完成实现清单转入本计划，不能仅凭代码测试通过勾销：

- [ ] 定向抽查真实失败案例的规划与重规划：确认 Agent 在必要勘察后提交有依据的 Step 标准，并在新证据确实改变标准时调用对应工具；结合官方结果和持久化轨迹判断。
- [ ] 观察更长任务中停用标准的累积是否显著增加常驻 Context。只有实际出现压力或恢复问题，再评估运行时视图优化，不预先加入截断机制。
