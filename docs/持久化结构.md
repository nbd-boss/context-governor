# Context Governor 持久化结构

本文用于理解和规划 Context Governor 的目标结构，重点说明各层为什么存在、信息的权威来源以及它们如何协作。

它不是字段级接口文档；实际实现、工具入口与测试方式以仓库中的 `src/`、`tests/` 和 [README](../README.md) 为准。

本文继续使用“修复 timeout 重试导致重复扣款”作为示例。

## 1. 设计目标

Context Governor 需要同时做到：

- 新 Context 能快速知道整个任务做到哪里；
- 已完成结论可以直接复用，避免重复执行；
- 精确明细可以按需读取，不常驻占用 token；
- 所有结论都能回到原始 History 核对；
- 每类信息只有一个持久化权威源；
- Epoch 内推进与 Epoch 边界持久化相互解耦。

## 2. 四层结构

```text
State
  ↓ 定位当前 Step
SubState
  ↓ 引用可复用的精确结果
Artifact
  ↓ 必要时回到原始证据
History
```

| 层级 | 回答的问题 | 保存内容 |
| --- | --- | --- |
| State | 整个任务做到哪里？ | 总目标、Step 计划、约束、生命周期 |
| SubState | 当前或某个 Step 内做到哪里？ | 已完成 SubStep、当前 SubStep、证据与 Artifact 引用 |
| Artifact | 哪些精确结果可以直接复用？ | 结果摘要、关键事实、可读取字段和资源位置 |
| History | 这些结论最初来自哪里？ | DSH Session 的原始消息、工具调用和工具结果 |

Audit 是旁路记录，只回答 Governor 何时构建、读取或切换 Context，不承载任务事实。

术语关系：

- `Step`：任务计划中的一个主要步骤；
- `SubState`：一个 Step 对应的子状态；
- `SubStep`：该 Step 内一个已经完成或正在执行的有边界动作；
- `Artifact`：某个 SubStep 产生、后续需要精确复用的结果。

Step 在完成必要勘察并规划后才创建唯一 SubState；一个 SubState 可以包含多个 SubStep；一个 SubStep 可以产生或使用多个 Artifact。

## 3. Session 隔离的目录

每个 DSH Session 拥有独立 Context Workspace：

```text
.context-governor/
└─ sessions/
   └─ session-payment-001/
      ├─ state.json
      ├─ sub_states/
      │  ├─ step-000001.json
      │  └─ step-000002.json
      ├─ artifacts/
      │  ├─ artifact-000001.json
      │  └─ artifact-000002.json
      ├─ transition/
      │  ├─ manifest.json
      │  └─ staging/
      └─ audit/
```

原始 History 仍由 DSH Session 日志保存，Governor 不复制整份 Trace。

开发阶段不迁移旧格式；旧测试数据可以直接舍弃。

## 4. State：全局任务状态

State 只保存任务级信息，不展开 Step 内部过程。

```json
{
  "schema_version": 1,
  "revision": 3,
  "mission": "修复 timeout 重试导致的重复扣款问题。",
  "task_plan": {
    "next_step_number": 4,
    "completion_criteria": [
      "能够稳定复现并解释重复扣款。",
      "同一重试链路只产生一笔 charge。",
      "相关回归测试全部通过。"
    ],
    "superseded_criteria": [],
    "steps": [
      {
        "step_id": "step-000001",
        "step": "复现重复扣款并保存证据。",
        "status": "done",
        "covers": [0]
      },
      {
        "step_id": "step-000002",
        "step": "定位 retry 与 idempotency key 的边界。",
        "status": "in_progress",
        "covers": [0]
      },
      {
        "step_id": "step-000003",
        "step": "修复实现并运行回归测试。",
        "status": "pending",
        "covers": [1, 2]
      }
    ]
  },
  "user_constraints": [
    "不修改数据库 schema。"
  ],
  "next_constraint_number": 1,
  "discovered_constraints": [],
  "lifecycle": {
    "status": "active"
  }
}
```

核心规则：

- `step_id` 是稳定身份，Step 改名时 ID 不变；
- `task_plan.next_step_number` 保存下一次身份分配序号，删除后也不回退，避免复用历史 ID；
- `task_plan.completion_criteria` 是任务级完成标准正文的唯一权威源；已有项不改写或重排，修订时只标记旧下标为 `superseded` 并追加新项；
- 每个 Step 的 `covers` 只引用任务级完成标准的数组下标，不复制标准正文；
- 所有 Step 合起来必须覆盖全部当前有效的任务完成标准；Pending Step 不得覆盖已替代标准；
- Step 的名称、顺序和状态只以 State 为准；
- `user_constraints` 只保存用户明确要求；
- `discovered_constraints` 只保存当前有效、已确认的运行边界，每项由 Governor 分配稳定的 `constraint_id`；
- `next_constraint_number` 是不回退的身份分配序号，替代旧约束后也不复用其 ID；
- `revision` 在每次成功的 State／SubState 更新事务后递增；
- State 不保存当前 SubStep、Artifact 明细、原始工具输出或可推导计数。

Step 规划时使用的 `inputs` 和 `result` 只用于明确规划边界，Governor 校验后立即丢弃。State 不保存这些规划期字段。Step 自身更详细的完成标准在该 Step 激活、必要勘察并调用 `plan_current_step` 后进入对应 SubState，不在 State 中重复保存。

当前 SubState 不需要额外指针。Governor 从唯一的 `in_progress` Step 获得 `step_id`，再找到对应 SubState。

运行时约束的两个记录入口共用新增／替代逻辑。输入必填 `replaces`：`[]` 新增独立约束；例如 `["constraint-000001"]` 表示用新证据支持的新约束替代这个有效条目。Governor 验证事件引用、版本、被替代 ID 和最终结构后一次提交；错误不部分写入。旧约束从当前 State 移除，历史仍保留在原始工具调用中；`replaces` 不重复保存到有效约束正文。Agent 比较当前及同批约束的语义，不由 Governor 自动判断冲突。

例如，替代成功后的有效条目可以是：

```json
{
  "constraint_id": "constraint-000002",
  "kind": "retry_safety",
  "condition": "请求超时且最终执行结果尚未确认。",
  "required_behavior": "先核对原请求的最终结果，再决定是否重新提交。",
  "source_events": ["event-42"]
}
```

普通任务事实属于 SubState／Artifact，未验证猜测和恢复方案属于 History／Continuation，不应混进已确认约束。提交可信结论前应区分请求参数、实际观测与推断；引用存在不等于结论已经得到支持。

### 4.1 任务执行状态

```text
working
= lifecycle.status 为 active
+ 恰好一个 Step 为 in_progress

finalizing
= lifecycle.status 为 active
+ 所有 Step 均为 done

completed
= lifecycle.status 为 completed
+ 所有 Step 均为 done
```

所有业务执行和验收都应在 Step 内完成。`finalizing` 只负责确认终态并调用完成工具。

如果进入 `finalizing` 后发现仍需工作，不重新打开已经完成的 Step，而是追加一个新的修正 Step，并将它设为 `in_progress`。这样已经完成的记录保持不可变。

## 5. SubState：一个 Step 的子状态

Step 首次进入 `in_progress` 时可先勘察；确认标准并调用 `plan_current_step` 后才创建 SubState。尚未开始的 Step 不创建 SubState。

```json
{
  "schema_version": 1,
  "step_id": "step-000002",
  "next_sub_step_number": 4,
  "step_completion_criteria": [
    {
      "criterion_id": "criterion-000003",
      "criterion": "retry 调用链已经确认。"
    },
    {
      "criterion_id": "criterion-000004",
      "criterion": "idempotency key 的生成位置已经确认。"
    }
  ],
  "superseded_criterion_ids": [],
  "completed_sub_steps": [
    {
      "sub_step_id": "sub-step-000002",
      "action": "追踪 retry() 到 create_charge() 的调用链。",
      "covers": ["criterion-000003"],
      "summary": "已完成调用链追踪。",
      "criterion_evidence": [
        {
          "criterion_id": "criterion-000003",
          "source_events": ["event-42", "event-47"]
        }
      ],
      "artifact_refs": [
        {
          "artifact_id": "artifact-000001",
          "relation": "produced"
        }
      ]
    }
  ],
  "current_sub_step": {
    "sub_step_id": "sub-step-000003",
    "action": "确认 create_charge() 是否在每次调用时生成新 key。",
    "covers": ["criterion-000004"],
    "continuation": null
  },
  "pending_sub_steps": []
}
```

SubState 的原则：

- `step_id` 是 SubState 的唯一身份，文件名为 `sub_states/<step_id>.json`；不再另设 SubState ID，也不复制 Step 名称和状态；
- `next_sub_step_number` 保存本 SubState 的身份分配进度；分配新 SubStep 时也考虑其他 SubState 的分配进度，保证跨 Step、删除和重启都不复用历史 ID；
- `step_completion_criteria` 是当前 Step 完成标准正文的唯一权威源；已有项不改写，修订时标记旧 ID 为 superseded 并追加新 ID；
- `completed_sub_steps` 只保存已验证、可复用、会影响后续工作的阶段结论；
- `current_sub_step` 恰好表示唯一正在执行的具体动作；
- `pending_sub_steps` 保存已经规划但尚未开始的动作，不保存状态或执行结果；
- `covers` 只引用本 SubState 中稳定的 `criterion_id`，不复制 Step 标准正文；SubStep 不再重复保存 `completion_criteria`；
- `current_sub_step.continuation` 保存尚未完成工作的最小恢复导航；没有交接信息时为 `null`，等待外部输入时可保存纯文本说明并使用空 `working_resources`；
- `criterion_evidence` 为每个已覆盖的 `criterion_id` 分别引用当前 Session 的原始证据；
- Artifact 只保存引用，不把 Artifact 内容复制进持久化 SubState。

如果 SubStep 没有 Artifact，`summary` 可以保存最小的可复用结论；如果已有 Artifact，`summary` 只说明阶段结果，具体事实以 Artifact 的 `contains.key_facts` 为准。

SubStep 只按 `pending_sub_steps → current_sub_step → completed_sub_steps` 移动；所在区域就是状态，因此不保存额外 `status`。完成 Current 后，Governor自动激活第一个 Pending，不要求 Agent重复提交 action。最后一个 Current 只能通过 Step 边界操作原子完成：它变为 Completed、`current_sub_step` 变为 `null`、State 中该 Step 同时变为 `done`。

普通调整由 `revise_step`／`revise_substep` 每次新增、修改或删除一个 Pending 项，其他项保持原样，每次提交都保持标准完整覆盖。若标准本身需要修订，则一次提交标准追加／替代和相关 `changes` 操作数组，内部复用相同编辑逻辑，最终校验通过后统一落盘。Completed、Current 不改写。

如果当前 SubStep 尚未完成，但已产生值得下一 Epoch 继续使用的工作文件，则记录：

```json
{
  "continuation": {
    "progress": "已经收集课程 1 至 40 的公告。",
    "working_resources": [
      {
        "path": "E:\\context\\workspace\\announcements-working.json",
        "contains": "课程 1 至 40 的公告结果。"
      }
    ],
    "resume_from": "从课程 41 开始继续。"
  }
}
```

Continuation 不是已验证结论或 Artifact。它随当前 SubStep 保存在同一个 SubState 文件中；后续记录会覆盖旧值，不形成进度日志。完成当前 SubStep 时，Continuation 自动移除。

`record_continuation` 的 `operation` 仅控制本次调用：`save` 保存文件型进度后继续返回，`wait_for_input` 保存阻碍、必要输入与恢复动作后结束当前回合；二者均不推进 Step 或完成任务。`operation` 不复制进持久化结构。等待时没有工作文件可传 `working_resources: []`，不得为停止而编造资源；非空路径仍必须是真实工作区文件。再次收到消息不等于恢复条件已满足，应先核实所需输入。

## 6. Artifact：精确、可复用的中间产物

只有同时满足以下条件时才创建 Artifact：

- 后续需要精确复用，而不只需要一句结论；
- 结果已生成并通过同步验证；
- 重查或重算成本较高；
- 能通过工作区文件和 History 追溯来源。

```json
{
  "schema_version": 1,
  "artifact_id": "artifact-000001",
  "contains": {
    "kind": "code_trace",
    "summary": "retry() 到 create_charge() 的完整调用链。",
    "coverage": "支付重试入口到网关扣款调用。",
    "key_facts": [
      "retry() 会在每次尝试中调用 create_charge()。",
      "retry() 没有向下传递稳定的 idempotency key。"
    ],
    "available_fields": [
      "caller",
      "callee",
      "file_path",
      "line_range",
      "passed_arguments"
    ]
  },
  "resource": {
    "path": "E:\\context\\test\\retry_billing\\retry-call-chain.json",
    "format": "json",
    "content_sha256": "abc123..."
  }
}
```

Artifact 只有两个核心部分：

- `contains`：告诉 Agent 这个结果是什么、覆盖什么、哪些结论可直接用、还有哪些明细字段；
- `resource`：告诉 Governor 精确内容在哪里，以及如何校验内容未变化。

MVP 中一个 Artifact 对应一个结构化 Resource，格式限于 JSON、JSONL 或 CSV。一个 SubStep 产生多个文件时，分别创建多个 Artifact。

Artifact ID 由 Governor 在 Session 内单调分配。已经提交的 Artifact 不覆盖；内容变化时创建新 Artifact。

### 6.1 Key Facts

`key_facts` 是 Resource 直接支持、经过验证的最小充分事实集合。每条事实应当：

- 范围明确；
- 具体且能独立理解；
- 一条只表达一个核心事实；
- 对后续判断有用；
- 不包含猜测、建议或下一步动作。

例如，保存 30 个未提交作业时：

```json
{
  "coverage": "以 2026-10-01 10:00:00+08:00 为快照，覆盖 12 门课程。",
  "key_facts": [
    "该快照中共有 30 个未提交作业。",
    "2026-10-08 10:00:00+08:00 前共有 8 个作业截止。"
  ],
  "available_fields": [
    "course_code",
    "assignment_title",
    "deadline",
    "points"
  ]
}
```

只判断数量时直接使用 Key Facts；需要生成 30 行 CSV 时才读取 Resource。

### 6.2 引用关系

持久化 SubState 只保存：

```json
{
  "artifact_id": "artifact-000001",
  "relation": "produced"
}
```

关系只有两种：

- `produced`：该 SubStep 创建此 Artifact；
- `used`：该 SubStep 使用已有 Artifact。

一个 Artifact 必须且只能有一个 `produced` 关系，可以有多个 `used` 关系。生产与使用关系只以 SubState 为准；Artifact 不重复保存 owner 或 provenance。

### 6.3 路径、验证与读取

Resource 路径必须是当前允许工作区中的规范化绝对路径。注册 Artifact 前，Governor 同步验证：

- 文件存在且格式受支持；
- 当前 SHA-256 与声明一致；
- `contains` 中的范围、事实和字段可由 Resource 直接支持；
- 对应 SubStep 的 History 证据存在。

读取 Artifact 时重新计算 Resource 哈希。哈希不一致时，读取操作返回临时的 `stale` 状态并拒绝提供可信内容；不会修改不可变的 Artifact 文件。Agent 若要使用新内容，必须重新验证并注册新的 Artifact。

## 7. History 与 Audit

History 是当前 DSH Session 的原始事件流：用户消息、Assistant 消息、工具调用和工具结果。

SubState 只保存 `event-N`，不保存 Session ID，也不复制原始事件。本设计不支持跨 Session 的 History 引用。

读取顺序是：

```text
SubState 结论足够
→ 直接使用

需要精确明细
→ 读取 Artifact

需要核对来源或 Artifact 仍不足
→ 读取少量 History 事件

旧信息不存在或必须获取最新状态
→ 调用外部工具
```

Audit 独立记录 Context 构建、按需读取、Epoch 切换与失败，不参与 State、SubState 或 Artifact 的语义。

## 8. 运行时索引与常驻 Context

State 中的 `task_plan.steps` 已提供全部 Step 的身份、名称和状态，直接作为全局导航。Governor 不再生成或注入重复的导航索引；需要某个 Step 的详细结论时，使用其 `step_id` 调用 `read_sub_state`。

每个新 Epoch 的常驻 Context 包含：

```text
完整 State
+ 当前 in_progress Step 的完整运行时 SubState 视图
+ 固定检索与切换规则
```

运行时 SubState 视图在 `artifact_catalog` 中展示所引用 Artifact 的 `artifact_id` 与 `contains`，按首次引用顺序排列，每个 Artifact 只出现一次。各 SubStep 的 `artifact_refs` 继续只保存 ID 和关系。Agent 先看目录中的 Key Facts，再决定是否调用 `read_artifact` 读取 Resource 正文。常驻 Context 与 `read_sub_state` 使用同一视图；目录仅在构建本次视图时派生，不写回 SubState，也不记录跨 Epoch 的“已读”标记。显式读取 Artifact 仍正常返回内容。

默认不注入：

- 已完成 Step 的完整 SubState；
- Artifact 的路径、哈希和 Resource 明细；
- 原始 History；
- Audit。

按需导航：

```text
State.task_plan.steps → read_sub_state → artifact_refs → read_artifact → read_prior_epoch_range
```

`read_prior_epoch_range` 的起止 ID 相同时只读取一个事件，范围内包含当前窗口可见事件时拒绝回查。Audit 由实验脚本或开发者读取文件，不进入 Agent 工具表。

## 9. 即时持久化与 Epoch 切换

每次成功的 Governor 状态工具调用都校验完整 Workspace，并立即以可恢复事务提交 State／SubState 的变更。一次操作只增加一个 `State.revision`；过时 revision 被拒绝。当前 Epoch 的常驻快照是起点，之后以工具返回的最新状态为准。

```text
完成一个 SubStep → 同次提交其 SubState、State、已生产的 Artifact
继续在当前 Epoch 工作 → 后续更新继续即时落盘
Agent 决定切换或触发安全阈值 → 从最新持久化快照构建新 Epoch
```

`switch_context` 通过必填的 `new_discovered_constraints` 交接需要新增或替代的已确认约束，每项用 `replaces` 明确替代对象，无变更传 `[]`。非空列表全部校验通过后一次持久化到 State，再切换模型可见 Context 并记录 Epoch 审计；失败不切换。空列表不写状态，未变化的 SubState/Artifact 不重写，不新增约束存储层。

已有 Current SubStep 的恢复仍使用其 Continuation。每次切换的 `switch_context.reason` 都作为独立运行时字段 `switch_note` 注入下一 Epoch，不论是否已有 SubState 或 Continuation；它只解释切换并补充必要的恢复线索，不覆盖或自动合并进 State/SubState/Continuation，也不是已完成或已验证结论。没有 Continuation 时，Agent 在此保留尚未持久化的必要进度、相关失败条件、已有文件位置、未决问题和下一动作；冲突时先核实证据，再通过正式工具更新状态。说明由原始工具调用和 Epoch 审计保留，不新增持久化状态字段；下一次切换只携带新的说明，不累积副本。

Governor 没有独立的常驻 token 预算。常驻消息完整构建，token 估算仅记录到 Audit；安全阈值针对完整 Context，默认是当前配置模型窗口的 80%。达到阈值后只允许收尾、交接和切换，不允许新建 SubState 继续扩大任务工作。

有 Artifact 的典型顺序是：

```text
注册并验证 Artifact
→ 完成当前 SubStep 并建立 produced 引用
→ 开始下一个 SubStep
```

每次状态提交前必须验证整个目标快照：

- Step、SubState 与 `step_id` 一一对应；
- `working`、`finalizing`、`completed` 状态合法；
- done Step 没有当前 SubStep；
- Artifact 引用存在，且每个 Artifact 恰有一个生产者；
- 提交所依据的 State revision 仍然有效。

提交采用 staging 和临时事务清单，Artifact 与 SubState 先落盘，目标 State 最后落盘。写入中断时，下一次访问可恢复事务。

事务清单和 staging 是恢复机制，不是任务事实的权威源。具体事务格式、写入顺序与恢复测试属于实现计划，不在本文固定。

Agent 尚未通过 Governor 工具提交的思考、草稿或业务文件不会自动成为已验证状态或 Artifact；这部分不属于当前恢复范围。

## 10. 权威来源

| 信息 | 唯一持久化权威源 |
| --- | --- |
| 总目标、Step 名称/顺序/状态、约束、生命周期 | State |
| Step 内已完成和当前工作 | SubState |
| SubStep 与 Artifact 的 produced/used 关系 | SubState |
| Artifact 的 Key Facts、可用字段、资源路径与哈希 | Artifact |
| 原始对话、调用和结果 | DSH History |
| Context 构建、读取与切换记录 | Audit |
| 展开后的 SubState | 运行时派生，不持久化 |

判断一条信息放在哪里：

```text
整个任务的目标、计划、约束或生命周期？ → State
某个 Step 内的阶段状态或结论？          → SubState
需要精确复用的已验证数据或文件？        → Artifact
原始执行记录？                          → History
Governor 的读取与切换行为？             → Audit
```

这套结构的核心不是保存更多内容，而是让每一层只保存自己负责的信息，并允许 Agent 从紧凑状态逐层下钻到精确数据和原始证据。
