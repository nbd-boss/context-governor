# Context Governor 持久化结构

本文用于理解和规划 Context Governor 的目标结构，重点说明各层为什么存在、信息的权威来源以及它们如何协作。

它不是字段级接口文档；实际实现、工具入口与测试方式以仓库中的 `src/`、`tests/` 和 [README](../README.md) 为准。

本文继续使用“修复 timeout 重试导致重复扣款”作为示例。

## 1. 设计目标

Context Governor 需要同时做到：

- 新 Context 能快速知道整个任务做到哪里；
- 已完成结论可以直接复用，避免重复执行；
- 精确明细可以按需读取，不常驻占用 token；
- 所有结论都能回到原始 History 核对；
- 每类信息只有一个持久化权威源；
- Epoch 内推进与 Epoch 边界持久化相互解耦。

## 2. 四层结构

```text
State
  ↓ 定位当前 Step
SubState
  ↓ 引用可复用的精确结果
Artifact
  ↓ 必要时回到原始证据
History
```

| 层级 | 回答的问题 | 保存内容 |
| --- | --- | --- |
| State | 整个任务做到哪里？ | 总目标、Step 计划、约束、生命周期 |
| SubState | 当前或某个 Step 内做到哪里？ | 已完成 SubStep、当前 SubStep、证据与 Artifact 引用 |
| Artifact | 哪些精确结果可以直接复用？ | 结果摘要、关键事实、可读取字段和资源位置 |
| History | 这些结论最初来自哪里？ | DSH Session 的原始消息、工具调用和工具结果 |

Audit 是旁路记录，只回答 Governor 何时构建、读取或切换 Context，不承载任务事实。

术语关系：

- `Step`：任务计划中的一个主要步骤；
- `SubState`：一个 Step 对应的子状态；
- `SubStep`：该 Step 内一个已经完成或正在执行的有边界动作；
- `Artifact`：某个 SubStep 产生、后续需要精确复用的结果。

一个 Step 对应一个 SubState；一个 SubState 可以包含多个 SubStep；一个 SubStep 可以产生或使用多个 Artifact。

## 3. Session 隔离的目录

每个 DSH Session 拥有独立 Context Workspace：

```text
.context-governor/
└─ sessions/
   └─ session-payment-001/
      ├─ state.json
      ├─ sub_states/
      │  ├─ sub-state-000001.json
      │  └─ sub-state-000002.json
      ├─ artifacts/
      │  ├─ artifact-000001.json
      │  └─ artifact-000002.json
      ├─ transition/
      │  ├─ manifest.json
      │  └─ staging/
      └─ audit/
```

原始 History 仍由 DSH Session 日志保存，Governor 不复制整份 Trace。

开发阶段不迁移旧格式；旧测试数据可以直接舍弃。

## 4. State：全局任务状态

State 只保存任务级信息，不展开 Step 内部过程。

```json
{
  "schema_version": 1,
  "revision": 3,
  "mission": "修复 timeout 重试导致的重复扣款问题。",
  "task_plan": {
    "completion_criteria": [
      "能够稳定复现并解释重复扣款。",
      "同一重试链路只产生一笔 charge。",
      "相关回归测试全部通过。"
    ],
    "steps": [
      {
        "step_id": "step-000001",
        "step": "复现重复扣款并保存证据。",
        "status": "done",
        "covers": [0]
      },
      {
        "step_id": "step-000002",
        "step": "定位 retry 与 idempotency key 的边界。",
        "status": "in_progress",
        "covers": [0]
      },
      {
        "step_id": "step-000003",
        "step": "修复实现并运行回归测试。",
        "status": "pending",
        "covers": [1, 2]
      }
    ]
  },
  "user_constraints": [
    "不修改数据库 schema。"
  ],
  "discovered_constraints": [],
  "lifecycle": {
    "status": "active"
  }
}
```

核心规则：

- `step_id` 是稳定身份，Step 改名时 ID 不变；
- `task_plan.completion_criteria` 是任务级完成标准正文的唯一权威源，初始化后不修改；
- 每个 Step 的 `covers` 只引用任务级完成标准的数组下标，不复制标准正文；
- 所有 Step 合起来必须覆盖全部任务完成标准；
- Step 的名称、顺序和状态只以 State 为准；
- `user_constraints` 只保存用户明确要求；
- `discovered_constraints` 只保存执行中确认、会持续约束后续工作的运行边界；
- `revision` 在一次 Epoch 边界提交成功后递增；
- State 不保存当前 SubStep、Artifact 明细、原始工具输出或可推导计数。

Step 规划时使用的 `inputs` 和 `result` 只用于明确规划边界，Governor 校验后立即丢弃。State 不保存这些规划期字段。Step 自身更详细的完成标准只在该 Step 激活后进入对应 SubState，不在 State 中重复保存。

当前 SubState 不需要额外指针。Governor 从唯一的 `in_progress` Step 获得 `step_id`，再找到对应 SubState。

### 4.1 任务执行状态

```text
working
= lifecycle.status 为 active
+ 恰好一个 Step 为 in_progress

finalizing
= lifecycle.status 为 active
+ 所有 Step 均为 done

completed
= lifecycle.status 为 completed
+ 所有 Step 均为 done
```

所有业务执行和验收都应在 Step 内完成。`finalizing` 只负责确认终态并调用完成工具。

如果进入 `finalizing` 后发现仍需工作，不重新打开已经完成的 Step，而是追加一个新的修正 Step，并将它设为 `in_progress`。这样已经完成的记录保持不可变。

## 5. SubState：一个 Step 的子状态

当 Step 第一次进入 `in_progress` 时创建 SubState。尚未开始的 Step 不创建 SubState。

```json
{
  "schema_version": 1,
  "sub_state_id": "sub-state-000002",
  "step_id": "step-000002",
  "step_completion_criteria": [
    {
      "criterion_id": "criterion-000003",
      "criterion": "retry 调用链已经确认。"
    },
    {
      "criterion_id": "criterion-000004",
      "criterion": "idempotency key 的生成位置已经确认。"
    }
  ],
  "completed_sub_steps": [
    {
      "sub_step_id": "sub-step-000002",
      "action": "追踪 retry() 到 create_charge() 的调用链。",
      "completion_criteria": [
        "确认关键函数和参数传递路径。"
      ],
      "covers": ["criterion-000003"],
      "summary": "已完成调用链追踪。",
      "source_events": ["event-42", "event-47"],
      "artifact_refs": [
        {
          "artifact_id": "artifact-000001",
          "relation": "produced"
        }
      ]
    }
  ],
  "current_sub_step": {
    "sub_step_id": "sub-step-000003",
    "action": "确认 create_charge() 是否在每次调用时生成新 key。",
    "completion_criteria": [
      "找到 key 的生成位置。",
      "用代码或测试证明重试生成了不同 key。"
    ],
    "covers": ["criterion-000004"],
    "continuation": null
  },
  "pending_sub_steps": []
}
```

SubState 的原则：

- 只通过 `step_id` 关联 State，不复制 Step 名称和状态；
- `step_completion_criteria` 是当前 Step 完成标准正文的唯一权威源；
- `completed_sub_steps` 只保存已验证、可复用、会影响后续工作的阶段结论；
- `current_sub_step` 恰好表示唯一正在执行的具体动作；
- `pending_sub_steps` 保存已经规划但尚未开始的动作，不保存状态或执行结果；
- `covers` 只引用本 SubState 中稳定的 `criterion_id`，不复制 Step 标准正文；
- `current_sub_step.continuation` 只保存尚未完成工作跨 Epoch 恢复所需的最小导航；没有阶段性文件时为 `null`；
- `source_events` 只引用当前 Session 的原始证据；
- Artifact 只保存引用，不把 Artifact 内容复制进持久化 SubState。

如果 SubStep 没有 Artifact，`summary` 可以保存最小的可复用结论；如果已有 Artifact，`summary` 只说明阶段结果，具体事实以 Artifact 的 `contains.key_facts` 为准。

SubStep 只按 `pending_sub_steps → current_sub_step → completed_sub_steps` 移动；所在区域就是状态，因此不保存额外 `status`。完成 Current 后，Governor自动激活第一个 Pending，不要求 Agent重复提交 action。最后一个 Current 只能通过 Step 边界操作原子完成：它变为 Completed、`current_sub_step` 变为 `null`、State 中该 Step 同时变为 `done`。

执行中需要调整尚未开始的计划时，可以整体替换 `pending_sub_steps`。Completed、Current 和 Step criteria 不变；新 Pending 获得全新 ID，变化先进入 Epoch Delta，并在 Context 切换时统一持久化。

如果当前 SubStep 尚未完成，但已产生值得下一 Epoch 继续使用的工作文件，则记录：

```json
{
  "continuation": {
    "progress": "已经收集课程 1 至 40 的公告。",
    "working_resources": [
      {
        "path": "E:\\context\\workspace\\announcements-working.json",
        "contains": "课程 1 至 40 的公告结果。"
      }
    ],
    "resume_from": "从课程 41 开始继续。"
  }
}
```

Continuation 不是已验证结论或 Artifact。它随当前 SubStep 保存在同一个 SubState 文件中；后续记录会覆盖旧值，不形成进度日志。完成当前 SubStep 时，Continuation 自动移除。

## 6. Artifact：精确、可复用的中间产物

只有同时满足以下条件时才创建 Artifact：

- 后续需要精确复用，而不只需要一句结论；
- 结果已生成并通过同步验证；
- 重查或重算成本较高；
- 能通过工作区文件和 History 追溯来源。

```json
{
  "schema_version": 1,
  "artifact_id": "artifact-000001",
  "contains": {
    "kind": "code_trace",
    "summary": "retry() 到 create_charge() 的完整调用链。",
    "coverage": "支付重试入口到网关扣款调用。",
    "key_facts": [
      "retry() 会在每次尝试中调用 create_charge()。",
      "retry() 没有向下传递稳定的 idempotency key。"
    ],
    "available_fields": [
      "caller",
      "callee",
      "file_path",
      "line_range",
      "passed_arguments"
    ]
  },
  "resource": {
    "path": "E:\\context\\test\\retry_billing\\retry-call-chain.json",
    "format": "json",
    "content_sha256": "abc123..."
  }
}
```

Artifact 只有两个核心部分：

- `contains`：告诉 Agent 这个结果是什么、覆盖什么、哪些结论可直接用、还有哪些明细字段；
- `resource`：告诉 Governor 精确内容在哪里，以及如何校验内容未变化。

MVP 中一个 Artifact 对应一个结构化 Resource，格式限于 JSON、JSONL 或 CSV。一个 SubStep 产生多个文件时，分别创建多个 Artifact。

Artifact ID 由 Governor 在 Session 内单调分配。已经提交的 Artifact 不覆盖；内容变化时创建新 Artifact。

### 6.1 Key Facts

`key_facts` 是 Resource 直接支持、经过验证的最小充分事实集合。每条事实应当：

- 范围明确；
- 具体且能独立理解；
- 一条只表达一个核心事实；
- 对后续判断有用；
- 不包含猜测、建议或下一步动作。

例如，保存 30 个未提交作业时：

```json
{
  "coverage": "以 2026-10-01 10:00:00+08:00 为快照，覆盖 12 门课程。",
  "key_facts": [
    "该快照中共有 30 个未提交作业。",
    "2026-10-08 10:00:00+08:00 前共有 8 个作业截止。"
  ],
  "available_fields": [
    "course_code",
    "assignment_title",
    "deadline",
    "points"
  ]
}
```

只判断数量时直接使用 Key Facts；需要生成 30 行 CSV 时才读取 Resource。

### 6.2 引用关系

持久化 SubState 只保存：

```json
{
  "artifact_id": "artifact-000001",
  "relation": "produced"
}
```

关系只有两种：

- `produced`：该 SubStep 创建此 Artifact；
- `used`：该 SubStep 使用已有 Artifact。

一个 Artifact 必须且只能有一个 `produced` 关系，可以有多个 `used` 关系。生产与使用关系只以 SubState 为准；Artifact 不重复保存 owner 或 provenance。

### 6.3 路径、验证与读取

Resource 路径必须是当前允许工作区中的规范化绝对路径。注册 Artifact 前，Governor 同步验证：

- 文件存在且格式受支持；
- 当前 SHA-256 与声明一致；
- `contains` 中的范围、事实和字段可由 Resource 直接支持；
- 对应 SubStep 的 History 证据存在。

读取 Artifact 时重新计算 Resource 哈希。哈希不一致时，读取操作返回临时的 `stale` 状态并拒绝提供可信内容；不会修改不可变的 Artifact 文件。Agent 若要使用新内容，必须重新验证并注册新的 Artifact。

## 7. History 与 Audit

History 是当前 DSH Session 的原始事件流：用户消息、Assistant 消息、工具调用和工具结果。

SubState 只保存 `event-N`，不保存 Session ID，也不复制原始事件。本设计不支持跨 Session 的 History 引用。

读取顺序是：

```text
SubState 结论足够
→ 直接使用

需要精确明细
→ 读取 Artifact

需要核对来源或 Artifact 仍不足
→ 读取少量 History 事件

旧信息不存在或必须获取最新状态
→ 调用外部工具
```

Audit 独立记录 Context 构建、按需读取、Epoch 切换与失败，不参与 State、SubState 或 Artifact 的语义。

## 8. 运行时索引与常驻 Context

全局 SubState 索引不持久化。Governor 在新 Epoch 开始时，根据 State 和 SubState 临时生成导航视图。

```json
{
  "sub_states": [
    {
      "sub_state_id": "sub-state-000001",
      "step_id": "step-000001",
      "sub_steps": [
        {
          "sub_step_id": "sub-step-1",
          "action": "构造 timeout 重试场景。"
        }
      ]
    }
  ]
}
```

索引只用于导航，不保存详细结论、Artifact 内容或可推导计数。

每个新 Epoch 的常驻 Context 包含：

```text
完整 State
+ 已完成 Step 的全局 SubState 导航索引
+ 当前 in_progress Step 的完整运行时 SubState 视图
+ 固定检索与切换规则
```

运行时 SubState 视图会把每个 `artifact_ref` 对应的 `contains` 原样附加进来，使 Agent 先看到 Key Facts，再决定是否读取 Artifact Resource。这个展开结果不写回 SubState。

默认不注入：

- 已完成 Step 的完整 SubState；
- Artifact 的路径、哈希和 Resource 明细；
- 原始 History；
- Audit。

按需导航：

```text
全局索引 → read_sub_state → artifact_refs → read_artifact → read_event
```

## 9. Epoch Delta 与边界提交

Epoch 内状态变化先按发生顺序记录到内存 Delta，不立即重写持久化文件。

```text
完成一个 SubStep
→ 记录 Delta
→ 继续在当前 Epoch 工作

Agent 决定切换，或触发安全阈值
→ 校验完整目标状态
→ 一次性提交 State、SubState 和 Artifact
→ 用新状态构建下一个 Epoch
```

Delta 以本 Epoch 开始时的 `State.revision` 为基础。提交时 revision 已变化则拒绝提交，避免覆盖别的状态。

有 Artifact 的典型顺序是：

```text
注册并验证 Artifact
→ 完成当前 SubStep 并建立 produced 引用
→ 开始下一个 SubStep
```

边界提交前必须验证整个目标快照：

- Step、SubState 与 `step_id` 一一对应；
- `working`、`finalizing`、`completed` 状态合法；
- done Step 没有当前 SubStep；
- Artifact 引用存在，且每个 Artifact 恰有一个生产者；
- Delta 的基础 revision 仍然有效。

提交采用 staging 和临时事务清单，Artifact 与 SubState 先落盘，目标 State 最后落盘。事务可以安全重放；只有完整提交成功后才切换可见 Context。

事务清单和 staging 是恢复机制，不是任务事实的权威源。具体事务格式、写入顺序与恢复测试属于实现计划，不在本文固定。

Epoch 边界前进程崩溃时，尚在内存中的 Delta 可能丢失；工作区业务文件仍保留，但不能自动当作已验证 Artifact。更完整的 Epoch 内断点恢复不属于当前 MVP。

## 10. 权威来源

| 信息 | 唯一持久化权威源 |
| --- | --- |
| 总目标、Step 名称/顺序/状态、约束、生命周期 | State |
| Step 内已完成和当前工作 | SubState |
| SubStep 与 Artifact 的 produced/used 关系 | SubState |
| Artifact 的 Key Facts、可用字段、资源路径与哈希 | Artifact |
| 原始对话、调用和结果 | DSH History |
| Context 构建、读取与切换记录 | Audit |
| 全局导航索引、展开后的 SubState | 运行时派生，不持久化 |

判断一条信息放在哪里：

```text
整个任务的目标、计划、约束或生命周期？ → State
某个 Step 内的阶段状态或结论？          → SubState
需要精确复用的已验证数据或文件？        → Artifact
原始执行记录？                          → History
Governor 的读取与切换行为？             → Audit
```

这套结构的核心不是保存更多内容，而是让每一层只保存自己负责的信息，并允许 Agent 从紧凑状态逐层下钻到精确数据和原始证据。
