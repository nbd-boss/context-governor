# 对照实验问题分析

本文用于讨论 LOCA 对照实验中，为什么相同固定条件下 Baseline 成功、而 Governor 未成功。它不是 Governor 的缺陷清单；每个观察都必须在对照原始运行轨迹后，才能判断是否属于上下文管理问题。

## 当前待处理问题

以下编号用于后续逐项讨论，不与本文既有案例小节编号混用。

### 问题 2：其他正确性策略仍不稳定

**现象：** 已加入的证据边界与精确数据传输策略能够在单次定向复跑中改善结果，但在相同冻结 Fixture 的重复运行中并不稳定。

```text
库存任务：成功 → 失败 → 成功
NHL 任务：成功 → 结果错误 → 60 分钟未完成
```

**当前结论：**

```text
策略能提高正确率
≠
策略能保证模型每次正确执行
```

**处理顺序：** 先比较同一任务成功与失败运行的首次行为分歧，确认是规划阶段遗漏、执行阶段未遵守，还是 Governor 在推进边界缺少可确定的约束；不得先为单一任务追加特化规则。

### 问题 3：某些任务的执行效率不可控

**现象：** NHL 的一次 Governor 运行在 60 分钟内没有完成：

```text
持续读取、重建、计算、验证
→ 一直没有结束当前 ACP 回合
→ Adapter 到 60 分钟后中止
```

**当前结论：** Adapter 的硬超时已经正确生效；未完成不是被误判为完成。但 Agent 的工作拆分、结束判断、重复探索或 Context 切换仍可能使总运行时间不可控。

**处理顺序：** 在不混入正确性判断的前提下，分析超时轨迹中的重复读取、恢复后重复探索、无进展 Epoch 与过大 SubStep；只有确认 Governor 造成可重复额外开销后，才修改 Governor。

### 问题 4：两次实验因 Node 堆内存不足而未启动

**现象：** 两个实验运行出现：

```text
JavaScript heap out of memory
```

即：

```text
DSH / Adapter Node 进程
→ 内存不足
→ 进程崩溃
→ Agent 没有获得完整执行机会
```

**当前结论：** 这是实验基础设施失败，不能用于评价 Governor 的正确性、效率或业务推理能力。

**处理顺序：** 单独定位 Node 进程的内存上限、累积对象或运行环境限制；修复后重新运行对应条件。该修复只能位于 Adapter / DSH 运行配置，不能向 Governor 注入实验基础设施逻辑。

## 2. 第一优先级：Governor 未完成的 2 个配对

这 2 个条件的含义是：Baseline 已完成且得到官方 Verifier 结果，而 Governor 在任务完成前停止，因而没有可用于成功/失败判定的最终产物。

它们不能简单归类为“Governor 答案错误”，但它们是 Governor 的可靠性问题：实际使用中，未完成任务同样不能交付结果。

分析时需要确认：

1. **停止原因**：是上下文窗口安全阈值、运行时间限制、单次输出上限、工具调用失败，还是 Agent 主动终止。
2. **停止时的 Governor 状态**：当前 Step、SubState、pending SubStep、Artifact 与 Epoch Delta 分别是什么。
3. **是否本可继续**：若已有明确的下一步与足够剩余预算，却在切换或恢复环节停止，则优先视为 Governor / Adapter 控制链路问题。
4. **是否已正确保存进度**：即使本轮无法完成，也要确认 State、SubState 与 Artifact 是否能让后续运行可靠继续，而非遗失已完成工作。

只有在这两条运行的停止原因明确后，才能决定最小修改范围；不要预先假定是 Context Governor 本身造成。

### 2.1 已检查的停止事实

两条未完成运行均为 `NhlB2bAnalysisS2LEnv`：

| seed | 窗口 | Governor 运行时长 | 停止原因 | Epoch / 切换 | 当时完成状态 |
| ---: | ---: | ---: | --- | ---: | --- |
| 2024 | 64K | 60.5 分钟 | `time_budget_exhausted` | 15 / 14 | `lifecycle: active`；1 个 SubState；未完成任务。 |
| 456 | 64K | 60.8 分钟 | `time_budget_exhausted` | 8 / 7 | `lifecycle: active`；尚未形成完成的 SubState；未完成任务。 |

两条记录均显示：

```text
不是 Governor 判断“任务已完成”而错误结束；
不是 State / SubState 校验失败；
不是 Context 窗口溢出；
而是 Adapter 的 60 分钟总运行预算到期时，Agent 仍在继续工作。
```

任务本身要求从 Google Sheet 中提取约 1,200 行 NHL 赛程，生成本地 CSV 和 Google Sheet。Agent 被 Google Sheet MCP 的范围读取行为困住：高行号读取会产生大量前导填充，返回内容又会被截断；它反复探索 spill 文件、公式、资源接口和分块范围读取方案。

### 2.2 与 Baseline 的事实性对比

同一条件的 Baseline 均完成：

| seed | Baseline 用时 | Baseline 工具调用 | Governor 工具调用 | 直接观察 |
| ---: | ---: | ---: | ---: | --- |
| 2024 | 38.5 分钟 | 293 | 334 | Governor 多次建立、保存、恢复读取策略，仍未完成完整提取。 |
| 456 | 43.9 分钟 | 158 | 约 18 次续跑后超时 | Governor 在中途持续校准读取/截断行为，未进入最终计算和写入。 |

这说明存在 **Governor 条件下的效率退化现象**：同一模型在同一 Fixture 中花费更多回合与更多时间在“如何读取数据”上，最终耗尽预算。

但目前还不能下结论说“Epoch 切换本身导致失败”。两个关键事实同时成立：

1. Governor 的常驻 Context 很小（约 1.7K–4.2K tokens），没有窗口溢出证据。
2. 任务工具的范围读取/截断语义本身困难，Baseline 的成功轨迹也经历了多次 `max_tokens` 和原生压缩。

下一步应精确比较每一次 Governor 切换前后的 SubState / continuation 与工具调用序列，确认 Agent 是否在恢复后重复探测已知死路，或是否缺少一个足以复用的“读取策略”中间成果。只有出现这种可重复的证据，才应修改 Governor。

### 2.3 处理决策：记录为后续效率优化

本节两条未完成运行当前归类为：

```text
效率风险：Governor 条件下，长任务可能因额外的读取探索、续跑和 Epoch 切换，
在固定总运行预算内无法完成。
```

它们不是已证实的数据损坏、状态丢失、错误完成判定或断点不可恢复问题。因此当前不针对这两条运行修改 Governor。

后续单列效率优化时，再验证并处理：

- Epoch 恢复后是否重复执行已证伪的工具策略；
- Continuation / SubState 是否应更明确保存“已尝试且不可用”的读取路径；
- 是否存在不必要的频繁切换与重复工具探测。

在此之前，分析优先级转向会直接破坏任务正确性或可恢复性的硬性缺陷。

### 3.1 `UpdateMaterialInventoryS2LEnv / seed 456 / 64K`

这是正确性问题，不是效率问题。

任务要求处理所有“新付费订单”。该 Fixture 中 120 条 WooCommerce 订单均为 `processing`，即任务所指的已付款订单。Baseline 读取并处理了全部 120 条。

Governor 则根据创建时间相差一秒，自行推断只有订单 107–120（14 条）是“新订单”，把订单 1–106 排除。这个边界没有来自任务说明、订单状态或外部规则的证据。

```text
只统计 14 条订单
→ 少扣除原材料
→ Google Sheets 库存偏高
→ 最大可生产量偏高
→ WooCommerce 库存同步为偏高值
→ 官方 Verifier 失败
```

例如：Governor 得到 `CONSOLE_001=17`，而 Baseline 处理全部订单后得到 `CONSOLE_001=114`。BOM 计算、库存写入和同步在“14 条订单”这个错误前提下彼此一致，但整个任务结果错误。

Governor 当前的缺口是：未经任务证据支持的关键业务分类，被保存为可信 Artifact 并被后续 SubState 复用，最终任务仍被标记为 `completed`。

后续讨论方向：对于决定处理范围的关键筛选/分类结论，如何要求 Agent 保存其依据、覆盖范围与排除项，并在完成前做最小范围核对；不为“一秒时间差”添加特例。

#### 已确认的修复方向

已确认的修复方向是使用统一的证据边界策略，约束所有会改变任务范围或任务结果的推断。该策略最初使用 `EVIDENCE_BOUNDARY_GUIDANCE` 表达，当前已整合到 `DECISION_CHECKS`：

```text
在用推断缩小任务范围、排除候选对象、
或决定后续计算、写入、同步等外部动作之前，
必须具有来自用户要求、明确规格或当前工具结果的直接证据。

不得将时间接近、名称相似、排序位置等相关性，
当作范围边界或业务规则。

证据不足时，不得将推断持久化为可信结果、
标记相关工作完成，或据此执行后续动作；
应获取权威证据或保持工作未完成。
```

当前规则的权威来源及使用位置如下：

```text
DECISION_CHECKS
  → 通过常驻 Context 提供证据边界、勘察后核对与完成前检查

ADVANCE_TASK_PROGRESS_DESCRIPTION
  → 通过 formatDecisionCheck('before_completion') 复用完成前检查
  → 保留完成证据、推进分支和终态条件，不拼入整段规划 Guidance
```

不新增 Tool、Schema 或持久化字段。

修复后，使用相同冻结 Fixture（`seed 456 / 64K`）单独复跑 Governor：

```text

新的 `artifact-000001` 记录了正确的范围事实：

候选订单：120 条，ids 1–120
状态事实：120 条均为 processing；其他状态为空
处理范围：120 条，未排除任何订单
```

之后 Agent 正确得到：

```text
CONSOLE_001=114
DRESSER_002=127
ARMCHAIR_003=101
STOOL_004=121
```

并将库存同步为官方期望值 `86 / 3598 / 584 / 1675`。这说明新证据边界策略在该次复跑中阻止了“按创建时间秒数缩小订单范围”的错误。

该验证只证明一次定向运行有效；后续应在相同 Fixture 上重复运行，以确认稳定性。

### 3.2 `NhlB2bAnalysisS2LEnv / seed 42 / 64K`

这也是正确性问题。此前概览中“本地 CSV 正确”这一表述不准确：Governor 的 CSV 与 Google Sheet 完全一致，但二者共同引用了错误的赛程重建结果，因此一起错误。

任务要求从源 Google Sheet 的完整赛程计算相邻两天的背靠背组合。Governor 为避免把 1,200 行赛程直接放进 Context，分块读取后在工作区重建 `schedule_all.csv`，再由该文件生成两个交付物。

重建结果表面上通过了自己的检查：

```text
声称的记录数：1199
检查项：日期范围、每天最多 4 场、每天没有重复球队、8 支球队均出现
```

但将工作区的 `schedule_all.csv` 与源 Sheet 的实际行逐项比较，发现它不是完整、准确的副本：

```text
源 Sheet：1200 条比赛记录
重建文件：1199 条比赛记录

丢失：2025-10-26  Carolina Hurricanes @ Chicago Blackhawks
错误翻转：2025-07-27  应为 Buffalo Sabres @ Boston Bruins，
                         实际写成 Boston Bruins @ Buffalo Sabres
```

这两个错误恰好影响了四支球队的背靠背分类：

| 球队 | 正确结果 | Governor 结果 |
| --- | --- | --- |
| Boston Bruins | `56,58,47,49,210` | `57,58,46,49,210` |
| Buffalo Sabres | `54,55,46,63,218` | `54,55,47,62,218` |
| Carolina Hurricanes | `61,54,67,44,226` | `61,54,67,43,225` |
| Chicago Blackhawks | `58,55,48,42,203` | `58,54,48,42,202` |

因此问题不在最终 CSV 写入或 Google Sheet 同步：两者都正确复制了同一份错误计算表。首次错误发生在“从分块工具结果人工转写并合并为本地结构化数据”的阶段。

Governor 当时的 Step / SubState 只把“记录数相等”和少量结构不变量当作完成证据。它没有要求确认重建数据与源数据逐行对应，也没有识别出“源的完整性已验证”与“结果内部自洽”是两种不同的证据。

后续讨论方向：为任何由分块读取重建、且将支撑后续计算或外部写入的结构化数据，定义一种轻量的来源完整性验证。它应验证覆盖范围和记录对应关系，而不是只验证记录数与内部统计不变量；不能为 NHL 的日期、主客场或 CSV 格式添加专用规则。

#### 定向复跑验证

接入常驻 Context 的精确数据传输策略后，以相同冻结 Fixture 复跑 Governor：

```text
官方 Verifier：通过（accuracy = 1）
Governor lifecycle：completed
```

本次运行先检查了源 Sheet 是否存在可由脚本直接读取或导出的路径；确认工具结果的 spill 文件和源模拟器均无法从 Agent Sandbox 直接访问后，才采用模型重建这一兜底路径。

但与原运行不同，它没有将“合并后记录数看起来合理”视为充分证据，而是明确保存并核对：

```text
源范围：Sheet 行 2..1215
重建结果：1200 场比赛
范围核对：4 个分段的记录数相加为 1200
重叠核对：对行 661..960 的独立第二次提取，300/300 行完全一致
结构核对：日期、球队、重复记录和每天比赛数均通过检查
```

随后，两种独立计算方法都得到相同的 8 支球队统计；CSV 与最终 Google Sheet 也逐单元格一致，且均通过官方 Verifier。

这说明该 Guidance 在此轮运行中达成了预期行为：能程序化直传时优先寻找该路径；没有路径时允许重建，但不再把重建结果无条件当作源数据。单次复跑仍不足以证明稳定性，后续应重复运行确认。

### 3.3 `WoocommerceNewWelcomeS2LEnv`：欢迎邮件已发送，但 BigQuery 未标记

以下三个配对呈现相同的官方 Verifier 结果：

| seed | 窗口 | 首次新客户数 | 通过项 | 失败项 |
| ---: | ---: | ---: | --- | --- |
| 2024 | 64K | 57 | 新客户写入 BigQuery、保留原有客户、欢迎邮件内容与收件人 | 全部 57 位新客户的 `welcome_email_sent` 均为 `false` / 未设置日期 |
| 42 | 32K | 29 | 新客户写入 BigQuery、保留原有客户、欢迎邮件内容与收件人 | 全部 29 位新客户的 `welcome_email_sent` 均为 `false` / 未设置日期 |
| 42 | 64K | 56 | 新客户写入 BigQuery、保留原有客户、欢迎邮件内容与收件人 | 全部 56 位新客户的 `welcome_email_sent` 均为 `false` / 未设置日期 |

简单地说，Agent 完成了：

```text
识别新客户 → 写入 BigQuery → 发送欢迎邮件
```

但遗漏了同一业务流程中必要的最终状态更新：

```text
将 BigQuery 中对应客户的 welcome_email_sent 设为 true，
并写入 welcome_email_date。
```

这是“跨系统流程的一项必要副作用未完成或未核验”的现象。尚未分析其首次分歧，因此目前不能断言是任务规划、Epoch 恢复、工具调用参数还是 Agent 推理导致。

### 3.4 `WoocommerceNewWelcomeS2LEnv / seed 456 / 64K`：新客户正确，但原有客户被删除

该配对与 3.3 不同：51 位新客户都已正确写入 BigQuery、标记已发送欢迎邮件，且对应欢迎邮件也正确；但 BigQuery 中原有的 50 位客户有 20 位缺失。

```text
预期：50 位原有客户 + 51 位新客户
实际：30 位原有客户 + 51 位新客户
```

这不是显式 `DELETE`，而是一次错误的 upsert 身份匹配。

运行前，Agent 读到 BigQuery 中有 50 条既有客户，`woocommerce_id` 范围为 10..59，邮箱为 `@woocommerce.com`。随后它发现 51 位待同步的新客户中，有 20 位 `customer_id` 的数值恰好与既有 `woocommerce_id` 重合，但邮箱为不同的 `@mcp.com` 身份。

Agent 为避免重复，做出了未经充分验证的假设：

```text
customer_id 与 woocommerce_id 的数值相同
→ 同一个客户
→ 应 UPDATE 既有 BigQuery 行，而非 INSERT 新行
```

于是它执行的写入结果为：

```text
插入 31 位没有数值 id 冲突的新客户
更新 20 位数值 id 冲突的既有客户
总行数：50 + 31 = 81
```

但这 20 次 `UPDATE` 覆盖了旧客户的邮箱、姓名等资料，使旧客户在最终数据中“消失”。正确结果应保留原有 50 行，并新增全部 51 行。

因此首次错误不在邮件发送或最终核对，而在同步 Step 将 `customer_id` 与 `woocommerce_id` 的数值重合视为跨系统身份映射时：它只依据数值重合推断身份相同，没有直接映射证据，且忽略了邮箱这一冲突身份属性。未证实的映射不应驱动对既有记录的更新、覆盖或删除；既有记录必须保留，映射关系应保持未解决。
